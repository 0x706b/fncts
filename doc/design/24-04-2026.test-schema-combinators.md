# Test Schema Combinators

## Goal

Write unit tests for each file of schema combinators in `packages/schema/src/Schema/api/`.

## Implementation Notes

- Tests should cover success and failure Parser cases.
- Tests should assert the structure of error return values
- Tests should follow the style of other tests in `packages/schema/test`
- Tests should use wrappers from @fncts/test/vitest
- Tests may use `Assertion` from @fncts/test
  - Using to test `Maybe` and `Either` equality is a good use case

## Scope Clarification

- For now, only test the primary combinators exported from each file.
- Do not add tests yet for helper transform constructors like `*FromArray`, `*FromRecord`, `eitherFromJson`, or `maybeFromNullable`.

## Implementation Findings

- Add one test file per primary combinator in `packages/schema/test/Schema/`:
  - `conc.test.ts`
  - `list.test.ts`
  - `maybe.test.ts`
  - `either.test.ts`
  - `map.test.ts`
  - `set.test.ts`
  - `hashSet.test.ts`
  - `hashMap.test.ts`
- Each test file should cover:
  - decode success for valid values
  - decode failure for wrong outer container type
  - decode failure for invalid member payloads
  - aggregated errors with `{ allErrors: true }` where supported by the parser
- Reuse `expectSuccess` and `expectFailure` from `packages/schema/test/utils.ts`.
- Match existing suite naming and error-structure assertions used by the other schema tests.

## Expected Coverage By Combinator

- `conc`
  - valid `Conc` decode
  - outer type failure
  - single invalid element failure
  - multiple invalid elements with `allErrors`
- `list`
  - valid `List` decode
  - outer type failure
  - single invalid element failure
  - multiple invalid elements with `allErrors`
- `maybe`
  - `Just(valid)` success
  - `Nothing()` success
  - outer type failure
  - `Just(invalid)` propagates inner error
- `either`
  - `Left(valid)` success
  - `Right(valid)` success
  - outer type failure
  - invalid left payload propagates left error
  - invalid right payload propagates right error
- `map`
  - valid `Map` decode
  - outer type failure
  - invalid key failure
  - invalid value failure
  - multiple collected key/value failures with `allErrors`
- `set`
  - valid `Set` decode
  - outer type failure
  - invalid member failure
  - multiple collected member failures with `allErrors`
- `hashSet`
  - valid `HashSet` decode
  - outer type failure
  - invalid member failure
  - multiple collected member failures with `allErrors`
- `hashMap`
  - valid `HashMap` decode
  - outer type failure
  - invalid key failure
  - invalid value failure
  - multiple collected key/value failures with `allErrors`

## Implementation Risks To Pin Down With Tests

- `list.ts` appears to keep the failing index at `0` instead of incrementing it for later elements.
- `set.ts` and `hashSet.ts` appear to place the schema in `KeyError.key` instead of the failing element value.
- `map.ts` and `hashMap.ts` wrap value parse failures in an extra `TypeError`, which may not match the intended error structure.
